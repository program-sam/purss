# Android and iOS apps

The phone and tablet apps: the web app's production build (`apps/web/dist`) bundled into a
[Capacitor](https://capacitorjs.com) 8 shell. There is no second interface: screens, styles and
behaviour come from `apps/web`, and what differs on a phone sits behind the platform layer in
`apps/web/src/platform/` (see [the web README](../web/README.md) and [plan/31](../../plan/31-mobile-apps.md)).
It talks to the PURSS it is connected to through the API with a device token
([plan/24](../../plan/24-connected-apps.md)), and installs the build of the interface that PURSS
offers when it fits the app's native code (live updates, [plan/39](../../plan/39-live-updates.md)).

| Path | What lives there |
| --- | --- |
| `capacitor.config.ts` | App id and name, the web build to bundle, the iOS share extension's app group, the updater plugin's settings |
| `native-level.json` | The native level live updates must match, and the fingerprint of the native side it was decided for (see below) |
| `scripts/app-bundle.ts`, `src/bundle.ts` | Packs the interface for live updates (the server image runs it) |
| `android/` | The Android project (Gradle). Generated by Capacitor, then edited: manifest, network rules, backups off, icons |
| `android/app/src/main/java/app/purss/device/` | The app's own native code (Kotlin, [plan/38](../../plan/38-phone-background-and-widgets.md)): the `PurssDevice` plugin (downloads that can be stopped), the background download job, the home-screen widget |
| `ios/App/` | The Xcode project: the app, its entitlements, and the `ShareExtension` and `Widgets` targets; `App/PurssDevice/` is the iOS side of the app's own plugin and background job |
| `scripts/emulator-workspace.ts` | A throwaway PURSS with a small library, for trying the app on an emulator or phone |
| `android/app/src/full/` | Full Android distribution's `PurssPushPlugin`, Firebase messaging service and fetcher (plan/37) |
| `android/app/src/fullDebug/` | Full debug builds only: a broadcast that runs what an arriving push runs, for the emulator |

Plugins (pinned; listed in both this package and `apps/web`, which imports them):
`@capacitor/app`, `browser`, `device`, `filesystem`, `network`;
`@aparajita/capacitor-secure-storage` (the device token), `@mediagrid/capacitor-native-audio`
(background audio with lock-screen controls), `@capgo/capacitor-share-target` (links shared from
other apps), `@capacitor/push-notifications` (notification permission, push address, taps on iOS),
`@capgo/capacitor-updater` (live updates of the interface, plan/39). The FOSS Android sync removes the push
plugin from Capacitor's generated dependency and registration lists. It also removes the passkey plugin's
optional Play Services provider and the updater's Play Store APK-update adapter; Android's Credential
Manager and the updater's live interface downloads remain. iOS and the full Android build keep the complete plugins.
Why each was chosen is in plan/31 and plan/37. `patches/` holds the app's changes to plugins (a file
`@scope+name.patch` changes `@scope/name`); `npm run sync` applies them to `node_modules` before the native
projects are built, and `npm test` checks they still fit the installed versions. The app's own plugins, `PurssDevice` (plan/38) and
`PurssPush` (plan/37), are registered in `MainActivity` (Android) and `MainViewController` (iOS).

## Build

```sh
npm ci
npm run sync -w @purss/mobile             # patches plugins (patches/), builds the web app for the apps' own
                                        # root (PURSS_WEB_BASE=/) and copies it and the plugin lists into android/ and ios/
```

**Android** needs Node.js 26, the Android SDK (platform 36), and JDK 21 (JDK 25 is too new
for the Android Gradle plugin used here).

```sh
cd apps/mobile/android
JAVA_HOME=<jdk 21> ANDROID_HOME=<sdk> ./gradlew assembleFullDebug
# app/build/outputs/apk/full/debug/app-full-debug.apk
```

**Version:** the product's ([plan/40](../../plan/40-versions.md)): versionName and versionCode come from the
checkout (`node scripts/version.ts --plain`) and Gradle reads them from the bundled interface's `app-build.json`.
Each build is higher than the last, as Google Play requires.

**Release signing** is the owner's own key, never committed (`*.jks`, `*.keystore` and
`keystore.properties` are ignored). Create a key with
`keytool -genkeypair -v -keystore release.jks -keyalg RSA -keysize 4096 -validity 10000 -alias purss`,
keep it outside Git with a backup, and put `keystore.properties` next to `android/settings.gradle`:

```properties
storeFile=/absolute/path/to/release.jks
storePassword=…
keyAlias=purss
keyPassword=…
```

`./gradlew assembleFullRelease` (or `bundleFullRelease` for Google Play) then signs with it; without
the file a release build is unsigned. The GitHub release workflow builds this full variant.

**Notifications** need the owner's Firebase project: put its `google-services.json` (Android app
`app.purss`) in `android/app/` before building. It is not committed (ignored in
`android/.gitignore`). Without it the build works and Settings → This device says this build can't
receive notifications. The relay that sends to it is `apps/push-relay`; the whole setup is in
[plan/37](../../plan/37-push-notifications.md#owner-steps). For Google Play, Play App Signing keeps the distribution key and
this one becomes the upload key.

## F-Droid build

The `foss` Android flavor has the same application id (`app.purss`) and app screens as the full build. It
does not include the Capacitor push-notifications plugin, Firebase Messaging, Google Play Services, Google
Play Core, the Google Services Gradle plugin, or the app's Firebase messaging service. Settings → This device
explains that this build can't receive phone notifications. Notifications inside PURSS, including the bell
and its settings, still work. Android's system Credential Manager and Capgo's live interface updates remain;
the FOSS build leaves APK updates to F-Droid. The default `full` flavor keeps phone push and is what GitHub
releases build.

Build an unsigned FOSS APK from a complete git checkout with Node.js 26, JDK 21 and Android SDK platform 36:

```sh
npm ci
npm run sync:foss -w @purss/mobile
cd apps/mobile/android
./gradlew assembleFossRelease --no-daemon -PpurssFoss=true
# app/build/outputs/apk/foss/release/app-foss-release-unsigned.apk
```

The sync builds the web interface with phone push disabled, applies FOSS-only adjustments to the two
third-party Android plugins, runs Capacitor sync for Android, then removes the push plugin dependency and
reflective registration from generated Android files. The updater compiles its Play Store API calls into the
same plugin that handles live updates, so excluding only Maven dependencies leaves unresolved Java references.
The FOSS sync applies exact, asserted source edits; its tests check that live updates remain, and the regular
sync restores the original npm plugin sources. Passkeys still use Android's Credential Manager. The FOSS build
also removes the Play Services and Play Store APK-update dependencies. Run the regular
`npm run sync -w @purss/mobile` before building the full variant again. The FOSS build uses the version
from the git checkout; F-Droid's recipe passes the `versionName` and `versionCode` recorded in its build
metadata. F-Droid signs the APK with its own key. Since Android treats signatures as part of app identity,
installing F-Droid over a GitHub-signed installation is blocked by Android. Switching requires an
uninstall, which erases the app's on-device data, including offline downloads and settings; the server
account is unaffected.

The draft metadata is in `apps/mobile/fdroid/`; the store text is in
`fastlane/metadata/android/en-US/`. Before submission, the owner should merge this work, choose
the first public release tag containing it, and set the metadata `commit` to that tag. Set the build's
`versionName` and `versionCode`, plus `CurrentVersion` and `CurrentVersionCode`, to the numeric version
from that tag (`node scripts/version.ts --plain`; PURSS uses the same number for both). In a fork of
[fdroiddata](https://gitlab.com/fdroid/fdroiddata), copy the YAML to
`metadata/app.purss.yml`, run its lint and build checks, and open a merge request. Reviewers will check that
the tagged source builds offline apart from declared npm and Maven dependencies, the APK has no Firebase
or Google Play Services classes, its version matches the metadata, and the app and all bundled licenses
are free. They may also ask for store screenshots and details about permissions or online services.

## Live updates and the native level

The app takes new builds of its interface from the server it is connected to, so a change to `apps/web` reaches
phones with a deploy instead of a store release ([plan/39](../../plan/39-live-updates.md)). It installs a build only
when the build's native level equals its own, so a store release is still needed when the native side changes in a
way the interface depends on.

`native-level.json` holds that level and a fingerprint of the native side. When you change anything under
`android/` or `ios/`, a plugin in `package.json` or `capacitor.config.ts`, `npm test` fails and names the new
fingerprint. Put it in the file, and raise `level` if the interface now needs the change (a plugin added, removed or
upgraded, a method of `PurssDevice` or `PurssPush`). Builds made at the new level then reach only apps built with it;
apps already installed keep the interface they have until they are updated from the store.

## Passkeys in the app

The app signs in and confirms it's you with the phone's own passkeys (`@capgo/capacitor-passkey`), the same
passkeys a browser uses on the PURSS's address, once the PURSS vouches for the app:

- **Android:** the PURSS sets `PURSS_APP_ANDROID_CERT_SHA256` to the SHA-256 fingerprint of the key that signs
  the APK (`keytool -list -v -keystore release.jks`, or the debug key's for a debug build) and serves
  `/.well-known/assetlinks.json`. Nothing to change in the app; any PURSS that vouches works.
- **iOS:** the PURSS sets `PURSS_APP_IOS_APP_ID` (`TEAMID.app.purss`), and the app has to be built with that
  domain: `PURSS_APP_PASSKEY_DOMAINS=purss.example npm run sync -w @purss/mobile`.

Elsewhere the app signs in with a username and password; links from emails (password reset,
confirming an address, invitations) are pasted into the app.

## Try it on the emulator

```sh
npm run build                                           # the PURSS's own build, served at /app/
node apps/mobile/scripts/emulator-workspace.ts 19990   # prints a username and password; Ctrl+C deletes everything
adb reverse tcp:19990 tcp:19990                          # the emulator's localhost is this computer
adb install -r apps/mobile/android/app/build/outputs/apk/full/debug/app-full-debug.apk
```

The app opens on the official server's sign-in; press **Use another server**, type
`http://localhost:19990`, and sign in with the username and password it printed. The app
remembers that server for next time. Plain HTTP works only for addresses on this device or the local network
(the rule in `packages/domain/src/workspace-address.ts`, shared with the extension); a PURSS
elsewhere needs HTTPS. Debug builds let Chrome's
`chrome://inspect` (or `adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`) inspect
the app's page.

### Background downloads and the widget on the emulator

The background job is a WorkManager periodic job (namespace `androidx.work.systemjobscheduler`). With
the app closed (Home, then `adb shell am kill app.purss`), find its id with
`adb shell dumpsys jobscheduler | grep app.purss` and run it with
`adb shell cmd jobscheduler run -f -n androidx.work.systemjobscheduler app.purss <id>`.
WorkManager skips a periodic run that comes before its hour is up ("executed before schedule" in
logcat); on an emulator, `adb root` and moving the clock forward an hour lets it run. A force-stopped
app has no jobs until it is opened again (Android's rule). Its log tag is `PurssBackground`. The widget
is in the launcher's widget list as *PURSS*. Kotlin unit tests:
`./gradlew testFullDebugUnitTest`.

### Notifications on the emulator

Without Firebase, a debug build can still go through everything but the push itself: point it at a
local relay with a stand-in push address, and run the messaging service's code with a broadcast that
exists only in debug builds.

```sh
PURSS_RELAY_PORT=8950 PURSS_RELAY_DATA_DIR=/tmp/purss-relay node apps/push-relay/src/main.ts &
PURSS_PUSH_RELAY_URL=http://localhost:8950 node apps/mobile/scripts/emulator-workspace.ts 19990
adb reverse tcp:19990 tcp:19990 && adb reverse tcp:8950 tcp:8950
cd apps/mobile/android && ./gradlew assembleFullDebug -PpurssPushRelay=http://localhost:8950 -PpurssPushDebugToken=emulator-debug-token-0123456789
```

Connect, turn on Settings → This device → Notifications on this phone (the system asks), make
something new reach the bell, then `adb shell am broadcast -a app.purss.DEBUG_PUSH -n
app.purss/.DebugPushReceiver`: the notification is fetched from the PURSS and shown, and
tapping it opens its item. (The PURSS's own wake goes nowhere here: it never calls an address on
this machine.)

## iOS: what to do on a Mac

The iOS project has not been compiled: it can't be on Linux. On a Mac with Xcode 16 or later:

1. `npm install && PURSS_WEB_BASE=/ npm run build -w @purss/web && cd apps/mobile && npx cap sync ios`, then
   `npx cap open ios` (opens `ios/App/App.xcodeproj`; plugins come through Swift Package Manager).
2. In *Signing & Capabilities*, choose your team for both the **App** and **ShareExtension**
   targets. If you change the app id, change both bundle ids (`app.purss`,
   `app.purss.ShareExtension`) and the app group everywhere it appears.
3. Register the app group `group.app.purss` in your Apple developer account (or let Xcode
   do it) and make sure both targets list it under *App Groups*; the files are
   `App/App.entitlements` and `ShareExtension/ShareExtension.entitlements`, and the same id is in
   `capacitor.config.ts` and `ShareExtension/ShareViewController.swift`.
4. Set the version ([plan/40](../../plan/40-versions.md)) from the checkout, in `ios/App`:
   `xcrun agvtool new-marketing-version "$(node ../../../../scripts/version.ts --dotted)"` and
   `xcrun agvtool new-version -all "$(node ../../../../scripts/version.ts --plain)"`.
5. Check *Background Modes → Audio* and *Background processing* on the App target (already in
   `Info.plist`, with `BGTaskSchedulerPermittedIdentifiers` = `app.purss.downloads`) and that
   the `purss` URL type is listed under *Info → URL Types*.
4a. The **Widgets** target (WidgetKit, `app.purss.Widgets`): choose your team and make sure it
   lists the app group under *App Groups* (`Widgets/Widgets.entitlements`). Check the small and medium
   widgets, light, dark and e-ink looks, and that tapping a row opens the item (`purss://open?item=…`).
4b. The background job: with a connected PURSS and automatic downloads on, send the app to the
   background, pause in the debugger and run
   `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"app.purss.downloads"]`,
   then open the app: the episode shows as Downloaded. Also check the Keychain read with the device
   locked after first unlock, and that a transfer still running when the task expires is finished
   when the system relaunches the app. Swift written without a compiler; signatures to check are
   listed in plan/38.
6. Notifications (the code is in `ios/App/App/PurssPushPlugin.swift` and `ios/App/NotificationService/`):
   - Add the *Push Notifications* capability to the **App** target (`aps-environment` in
     `App/App.entitlements`; Xcode switches it to production for distribution).
   - Register the keychain access group `app.purss.shared` (it appears as
     `$(AppIdentifierPrefix)app.purss.shared` in `App/App.entitlements`,
     `NotificationService/NotificationService.entitlements` and both `Info.plist` files as
     `PurssKeychainGroup`) and make sure both the **App** and **NotificationService** targets list it
     under *Keychain Sharing*. On the **App** target the app's own group (`app.purss`) must stay
     listed first: Keychain items without a named group (the device token) go to the first group, and
     the extension must never be able to read the device token. Choose your team for the **NotificationService** target too
     (bundle id `app.purss.NotificationService`; change it with the app id).
     The extension reads only that Keychain item, so it has no app group; the **App** target carries
     both, the app group shared with **ShareExtension** and **Widgets** and the keychain group shared
     with **NotificationService**.
   - In the Apple developer account create an APNs auth key (*Keys → Apple Push Notifications
     service*, a `.p8` file). Note its Key ID and your Team ID, and give the three to the relay
     (`apps/push-relay`).
   - On a device, check: Settings → This device → Notifications on this phone asks for permission;
     a notification from your PURSS shows its real text, not "You have something new in your
     PURSS."; tapping it opens the item (the same `purss://open` handling as a widget's row);
     turning the setting off stops notifications; and disconnecting the app, or the background job
     finding the device disconnected in the PURSS, stops them too and empties the widget.
7. Build and run on a simulator, then a device, and check: connecting (the browser returns to the
   app), reading, playing with the screen locked and the lock-screen controls, downloading and
   reading in airplane mode, and sharing a link from Safari (Share → PURSS).
8. For distribution: an App Store Connect record, an archive (*Product → Archive*) and TestFlight.
   App Review needs a reachable demo PURSS with sample data.

## The official server

The apps and the browser extension connect to the official server unless the person chooses
another one. Its address is `OFFICIAL_WORKSPACE_ORIGIN` in `packages/domain/src/distribution.ts`:
change that one value when the server moves (an empty string shows only the address field).
The app opens straight on its sign-in; nobody has to type or confirm a server.

Once the app is live in Google Play or the App Store, put the listing's address in `STORE_LISTINGS`
in `packages/domain/src/distribution.ts`: Settings → Connected apps and the website then show its
store button instead of "Not in the stores yet".

Things to watch on iOS: `@mediagrid/capacitor-native-audio` and `@aparajita/capacitor-secure-storage`
must resolve through Swift Package Manager (both ship a `Package.swift`); WebCrypto (`crypto.subtle`,
used for PKCE) is expected in the `capacitor://` page.
