# Android and iOS apps

The phone and tablet apps: the web app's production build (`apps/web/dist`) bundled into a
[Capacitor](https://capacitorjs.com) 8 shell. There is no second interface: screens, styles and
behaviour come from `apps/web`, and what differs on a phone sits behind the platform layer in
`apps/web/src/platform/` (see [the web README](../web/README.md)). It talks to the PURSS it is connected
to through the API with a device token (see [Connecting](#connecting)), and installs the build of the
interface that PURSS offers when it fits the app's native code ([Live updates](#live-updates-and-the-native-level)).
How people use the app is in the [user guide](../../docs/user-guide.md#the-phone-app); the trust model of
device tokens is in [security](../../docs/security.md#connected-apps).

| Path | What lives there |
| --- | --- |
| `capacitor.config.ts` | App id and name, the web build to bundle, the iOS share extension's app group, the updater plugin's settings |
| `native-level.json` | The native level live updates must match, and the fingerprint of the native side it was decided for (see below) |
| `scripts/app-bundle.ts`, `src/bundle.ts` | Packs the interface for live updates (the server image runs it) |
| `android/` | The Android project (Gradle). Generated by Capacitor, then edited: manifest, network rules, backups off, icons |
| `android/app/src/main/res/values/` | `strings.xml` and `widget_strings.xml` hold every text people read in the Android app (notifications, widgets, the widget picker's sample rows). They are written by `scripts/native-translations.ts` from `packages/translations/src/en/native.ts` (its `android` and `widget` sections): change the catalog and run `npm run translations:native`, never the files. `app_identifiers.xml` (application id, URL scheme) is not text and is edited by hand |
| `android/app/src/main/java/app/purss/device/` | The app's own native code (Kotlin): the `PurssDevice` plugin (downloads that can be stopped), the background download job, the home-screen widget |
| `ios/App/` | The Xcode project: the app, its entitlements, and the `ShareExtension` and `Widgets` targets; `App/PurssDevice/` is the iOS side of the app's own plugin and background job. The widgets' and notification extension's text is `Widgets/NativeTranslations.swift`, written by `scripts/native-translations.ts` from `packages/translations/src/en/native.ts` (its `widget` section, shared with Android, and `ios`); change the catalog and run `npm run translations:native`, never the file |
| `scripts/emulator-workspace.ts` | A throwaway PURSS with a small library, for trying the app on an emulator or phone |

Plugins (pinned; listed in both this package and `apps/web`, which imports them):
`@capacitor/app`, `browser`, `device`, `filesystem`, `network`, `share` (exports go to the share sheet);
`@aparajita/capacitor-secure-storage` (the device token), `@mediagrid/capacitor-native-audio`
(background audio with lock-screen controls), `@capgo/capacitor-share-target` (links shared from
other apps), `@capgo/capacitor-passkey` (the phone's passkeys), `@capacitor/push-notifications`
(notification permission, push address, taps on iOS) and `@capgo/capacitor-updater` (live updates of the
interface). The FOSS Android sync removes the push
plugin from Capacitor's generated dependency and registration lists. It also removes the passkey plugin's
optional Play Services provider and the updater's Play Store APK-update adapter; Android's Credential
Manager and the updater's live interface downloads remain. iOS and the full Android build keep the complete plugins.
`patches/` holds the app's changes to plugins (a file
`@scope+name.patch` changes `@scope/name`); `npm run sync` applies them to `node_modules` before the native
projects are built, and `npm test` checks they still fit the installed versions. The app's own plugins, `PurssDevice`
(downloads, the background job, the home-screen panels, the badge) and `PurssPush` (notifications), are registered in
`MainActivity` (Android) and `MainViewController` (iOS).

**Why this audio plugin.** `@mediagrid/capacitor-native-audio` runs playback in a Media3 `MediaSessionService`
declared as a `mediaPlayback` foreground service, which Android needs to keep playing with the screen off; it shows
the system media notification and lock-screen controls and reports play and pause from them; it streams URLs
(publishers' files) and plays local files. `@capgo/native-audio` leaves the foreground service to the app, and
`@capacitor-community/native-audio` is for short sounds. The plugin reports no position events, no errors and
seeks in whole seconds, and a native player outlives a page reload; `apps/web/src/platform/native/audio-backend.ts`
works around each (it reads the position every second while playing and on every pause, counts a file that isn't
ready within 30 seconds as failed, and destroys a leftover player first). On Android the plugin ignores its
skip-time options and leaves "next" and "previous" to Media3, which does nothing with one episode; the patch
(`patches/@mediagrid+capacitor-native-audio.patch`, applied by `scripts/patch-plugins.ts`) makes the session skip
30 s forward on next and 15 s back on previous (a headset's double press) and adds skip-15 and skip-30 buttons
to the notification. iOS is unchanged. Video plays in the page's media element, not in the plugin.

## Connecting

The app opens on the official server's sign-in (`OFFICIAL_WORKSPACE_ORIGIN` in `packages/domain/src/distribution.ts`);
**Use another server** under it reveals the address field, and the server last connected to is remembered, also after
disconnecting. Signing in goes one of two ways: email address and password (or the phone's passkey, see below) typed
in the app, or the system browser (Custom Tabs, SFSafariViewController) at the server's `/connect` page with PKCE (S256)
and a fresh `state`, which returns to `purss://connect` with a one-time code, `state` and the server's `iss`; the app
exchanges the code at `POST /api/connect/token`. A pending browser sign-in survives the app being stopped for ten
minutes. An external sign-in (*Continue with Google*) always opens the system browser, because providers refuse their
sign-in inside an app's web view. Device tokens, their lifetime and what a token reaches are described in
[security](../../docs/security.md#connected-apps).

- **Token and requests.** The token is kept in the iOS Keychain (`afterFirstUnlockThisDeviceOnly`, so playback with the
  screen locked can still save its position) or Android's Keystore-encrypted storage, never in local storage or an
  address. Every API request goes to the connected origin with `Authorization: Bearer` and no cookies; the transport
  refuses an absolute address on any other origin. The built `index.html` carries a Content-Security-Policy that
  allows any http(s) PURSS (the server is chosen at run time); once connected, a second policy for that origin is added
  before any request (connect, images and media from the PURSS and https publishers, frames only from the video players
  the reader embeds).
- **Addresses.** One rule with the browser extension (`parseWorkspaceAddress`, `packages/domain/src/workspace-address.ts`):
  HTTPS, except this device and the local network (private, CGNAT and link-local ranges, IPv6 unique-local and
  link-local, and the names `.local`, `.lan`, `.internal` and `.home.arpa`), where plain HTTP is allowed with a visible
  *not encrypted* note on the connect screen and in Settings → This device. Android's network rules can't list address
  ranges, so they permit clear text and the app enforces the rule (transport to the PURSS only, the page policy,
  https-only publisher files in downloads and the player); iOS uses `NSAllowsLocalNetworking` plus exceptions for
  `.lan`, `.internal` and `.home.arpa`. Passkeys don't work on an http address. Whether iOS's App Transport Security
  handles those local-name exceptions as intended has not been checked.
- **Offline.** The same `OfflineWorker` the web's service worker runs is called by the app's transport in the page, with
  copies in IndexedDB (`platform/copies.ts`): iOS's WKWebView runs service workers only for https app-bound domains,
  never for the app's `capacitor://` scheme, and API requests go to another origin anyway. Offline reading is on by
  default. The session and the lists a start without a connection shows come from those copies, so starting the app with
  no connection needs offline reading on; downloads alone don't start it. With it off, downloaded items are still read
  and played while the app is running.
- **Disconnecting.** Settings → This device → *Disconnect this app* calls `DELETE /api/connect/device` (8 seconds), then
  removes the token, offline copies, downloads, the notification registration, the background job and the home-screen
  panels' data, and the annotation outbox with unsent positions and progress after a warning when anything is unsent. A
  `401 device_signed_out` from any request or the event stream does the same with a notice, except that unsent
  highlights, notes, positions and progress stay, per account, and are sent when that account connects again. If the
  server can't be reached the device is still wiped and the person is told to remove it in Settings → Connected apps.
  If secure storage refuses to remove the token, the next start doesn't use it.
- **Positions made offline.** The player keeps every position on the device first and removes it once the server has it.
  What is left from playing without a connection is sent at start, when the connection returns, when the app is shown
  again and every ten seconds while any waits, with `recordedAt`; the server keeps the position recorded last, and
  opening an item resumes from the newer of the server's and the device's. Reading progress made offline is kept and
  sent the same way (`state/late-progress.ts`), only while it is ahead of the server's. Two devices' clocks can differ,
  so recording times are only as good as the device's clock.
- **Sharing in.** Android `ACTION_SEND text/plain` and an iOS share extension find the first web address in what was
  shared and ask **Keep link** or **Add as source** (prefilled; discovery starts only when the person presses Find).
  Only links are taken. `purss://connect`, `purss://share` and `purss://open` are the only links the app handles;
  `open` only navigates (an item, a list, or Home), so another app opening one can't make the app act.
- **Links from emails** (password reset, confirming an address, an invitation) are pasted into the app; they work with
  any PURSS, without app links on its domain.

## Build

```sh
npm ci
npm run sync -w @purss/mobile             # patches plugins (patches/), builds the web app for the apps' own
                                        # root (PURSS_WEB_BASE=/) and copies it and the plugin lists into android/ and ios/
```

**Android** needs Node.js 26, the Android SDK (platform 36), and JDK 21 (JDK 25 is too new
for the Android Gradle plugin used here).

```sh
cd apps/mobile/android
JAVA_HOME=<jdk 21> ANDROID_HOME=<sdk> ./gradlew assembleFullDebug
# app/build/outputs/apk/full/debug/app-full-debug.apk
```

**Version:** the product's, a seven-digit number from the commit's UTC day and its place among that day's commits
on `main` (`2631214` is the 14th commit of day 312 of 2026), so each build is higher than the last, as Google Play
requires. versionName and versionCode are that number: they come from the checkout (`node scripts/version.ts --plain`)
and Gradle reads them from the bundled interface's `app-build.json`. A build from a checkout without history has
versionCode `1` and versionName `dev`.

**Release signing** is the owner's own key, never committed (`*.jks`, `*.keystore` and
`keystore.properties` are ignored). Create a key with
`keytool -genkeypair -v -keystore release.jks -keyalg RSA -keysize 4096 -validity 10000 -alias purss`,
keep it outside Git with a backup, and put `keystore.properties` next to `android/settings.gradle`:

```properties
storeFile=/absolute/path/to/release.jks
storePassword=…
keyAlias=purss
keyPassword=…
```

`./gradlew assembleFullRelease` (or `bundleFullRelease` for Google Play) then signs with it; without
the file a release build is unsigned. The GitHub release workflow builds this full variant.

**Notifications** need the operator's Firebase project: put its `google-services.json` (Android app
`app.purss`) in `android/app/` before building. It is not committed (ignored in
`android/.gitignore`); the release workflow writes it from the repository secret `GOOGLE_SERVICES_JSON`. Without it the build works and Settings → This device says this build can't
receive notifications. The file names the Firebase project (ids and an API key restricted to the app) and ships in every
APK; it stays out of Git because it belongs to one operator's build, so a fork doesn't send to someone else's project by
accident. The relay that sends to the phone is `apps/push-relay`; the whole setup is in
[Phone notifications](#phone-notifications). For Google Play, Play App Signing keeps the distribution key and
this one becomes the upload key.

## F-Droid build

The `foss` Android flavor has the same application id (`app.purss`) and app screens as the full build. It
does not include the Capacitor push-notifications plugin, Firebase Messaging, Google Play Services, Google
Play Core, the Google Services Gradle plugin, or the app's Firebase messaging service. Settings → This device
explains that this build can't receive phone notifications. Notifications inside PURSS, including the bell
and its settings, still work. Android's system Credential Manager and Capgo's live interface updates remain;
the FOSS build leaves APK updates to F-Droid. The default `full` flavor keeps phone push and is what GitHub
releases build.

Build an unsigned FOSS APK from a complete git checkout with Node.js 26, JDK 21 and Android SDK platform 36:

```sh
npm ci
npm run sync:foss -w @purss/mobile
cd apps/mobile/android
./gradlew assembleFossRelease --no-daemon -PpurssFoss=true
# app/build/outputs/apk/foss/release/app-foss-release-unsigned.apk
```

The sync builds the web interface with phone push disabled, applies FOSS-only adjustments to the two
third-party Android plugins, runs Capacitor sync for Android, then removes the push plugin dependency and
reflective registration from generated Android files. The updater compiles its Play Store API calls into the
same plugin that handles live updates, so excluding only Maven dependencies leaves unresolved Java references.
The FOSS sync applies exact, asserted source edits; its tests check that live updates remain, and the regular
sync restores the original npm plugin sources. Passkeys still use Android's Credential Manager. The FOSS build
also removes the Play Services and Play Store APK-update dependencies. Run the regular
`npm run sync -w @purss/mobile` before building the full variant again. The FOSS build uses the version
from the git checkout; F-Droid's recipe passes the `versionName` and `versionCode` recorded in its build
metadata. F-Droid signs the APK with its own key. Since Android treats signatures as part of app identity,
installing F-Droid over a GitHub-signed installation is blocked by Android. Switching requires an
uninstall, which erases the app's on-device data, including offline downloads and settings; the server
account is unaffected.

The metadata is in `apps/mobile/fdroid/`; the store text is in
`fastlane/metadata/android/en-US/`. To submit, choose a release tag and set the metadata `commit` to it. Set the build's
`versionName` and `versionCode`, plus `CurrentVersion` and `CurrentVersionCode`, to the numeric version
from that tag (`node scripts/version.ts --plain`; PURSS uses the same number for both). In a fork of
[fdroiddata](https://gitlab.com/fdroid/fdroiddata), copy the YAML to
`metadata/app.purss.yml`, run its lint and build checks, and open a merge request. Reviewers will check that
the tagged source builds offline apart from declared npm and Maven dependencies, the APK has no Firebase
or Google Play Services classes, its version matches the metadata, and the app and all bundled licenses
are free. They may also ask for store screenshots and details about permissions or online services.

## Live updates and the native level

The app takes new builds of its interface from the server it is connected to, so a change to `apps/web` reaches
phones with a deploy instead of a store release. A store release is needed only for native work: plugins,
permissions, the Android and iOS projects. Every server image packs the interface built for the apps' root
(`PURSS_WEB_BASE=/`) as a zip with a `manifest.json` (`apps/mobile/scripts/app-bundle.ts`); `GET /api/app/bundle`
says what is on offer (version, native level, path, SHA-256, size) and `GET /api/app/bundle/<file>` serves that one
file. A self-hosted server offers its own build with no setup, so the interface always matches the API it talks to and
updating the server updates its apps. Without a packed build both answer 404 and the apps keep the interface they have.

- **When.** The app checks at start and again when shown (at most every 30 minutes), downloads the offer, and switches
  at the next start before anything is shown, or when shown again after at least an hour away with nothing playing. It
  never switches in the background: switching reloads the page, which would stop the player (the native player doesn't
  outlive a reload) and lose a half-written note. The plugin's own *next bundle* is installed when the app goes to the
  background, so the app keeps its own queue instead.
- **Rollback.** The interface reports that it started (`notifyAppReady`) before anything else. If it doesn't within 15
  seconds the plugin goes back to the previous interface, and the app remembers that version and never installs it again.
  With no offer, or after *Don't allow*, the app returns to the interface it was installed with at the next switch and
  deletes older downloads. Disconnecting returns to it straight away. A store update of the app removes downloaded
  interfaces (`resetWhenUpdate`), so the installed one runs until the server's build fits it.
- **Who may push code** (the trust model is in [security](../../docs/security.md#updates-of-the-phone-and-desktop-interface)).
  Any server the person connects to: bundles are not signed, and the SHA-256 only catches a damaged download. The
  official server's updates need no question. Any other server is asked about once, the first time it offers an update
  (*Let PURSS update the app?*); closing the question counts as *Don't allow*, the answer is kept per server, and
  *Settings → This device → Updates of the app* changes it. An installed interface is code running in the app, and it
  stays until the app is reinstalled or its data cleared. Downloads over plain http are allowed under the same address
  rule as the connection (`httpsOnly: false`).
- **No third party.** Capgo's service is not used: `autoUpdate` is off and `updateUrl`, `statsUrl` and `channelUrl` are
  empty, so no update check, statistic or channel goes anywhere. The app talks only to the connected PURSS and the push relay.

`native-level.json` holds the level an interface must match and a fingerprint of the native side. The app installs a
build only when the build's native level equals its own, read from its installed version (`native.built.0`, written by
the web build to `app-build.json` and set at `npm run sync`); otherwise it runs the interface it was installed with.
When you change anything under `android/` or `ios/`, a plugin in `package.json` or `capacitor.config.ts`, `npm test`
fails and names the new fingerprint. Put it in the file, and raise `level` if the interface needs the change (a
plugin added, removed or upgraded, a method of `PurssDevice` or `PurssPush` it can't do without; a method whose absence it
handles, such as `installSource`, needs no new level). Builds made at the new level then reach only apps built with it;
apps already installed keep the interface they have until they are updated, and the app tells people so. The desktop app
takes the same builds by the same rules at its own level (the offer's `desktop` field).

**The app's own new versions** (`platform/native/app-updates.ts`): Google Play, F-Droid and the App Store update
it themselves. `PurssDevice.installSource()` gives the build's flavor and the installing package: the FOSS build is
F-Droid, an install by `com.android.vending` is Google Play, any other full build (a browser, the package installer,
adb, an APK updater) is the GitHub releases, and iOS is the App Store. An app built before that method existed can't
tell and is never told to download anything. The full build installed any other way is taken to be the APK from the
GitHub releases: it reads the newest release's `latest.json` once a day (at start and when shown again) through
Capacitor's native HTTP and offers *Download* when its version is newer than the installed one; Download opens
`PURSS-android.apk` in the in-app browser and Android's installer installs it over the app, keeping its data. The app
doesn't install it itself, which would need the *install unknown apps* permission. When the server offers screens for
a higher native level than the app's and the person hasn't refused its updates, the app says once per installed version
that the newest screens need a newer app, and Settings keeps saying so.

Google Play allows an app to download JavaScript that runs in its WebView. Apple's guidelines allow interpreted code
that doesn't change the app's main purpose (2.5.2, and 3.3.1 of the developer agreement); whether App Review accepts the
iOS app with live updates hasn't been tested, as no iOS build has been submitted.

## Phone notifications

The apps show PURSS's notifications as system notifications, for the official server and for self-hosted ones, without
the self-hoster needing any account or configuration. Pushes carry no content: a relay run by the project
([`apps/push-relay`](../push-relay/README.md)) wakes the phone, and the phone fetches the text from its own PURSS.

1. **Registration.** When the person turns on *Settings → This device → Notifications on this phone* (or *Turn on* in
   the bell's one-time offer) the system's permission prompt appears, never at first launch. The app gets its push
   address (an FCM token on Android, an APNs token on iOS, through `@capacitor/push-notifications`) and registers it
   with the relay together with a random *scope* kept per connection; the relay answers with a handle, the same one for
   the same phone and scope and a different one for another connection, so two PURSSes can't tell that they reach the
   same phone. The app sends the handle to its PURSS (`POST /api/push/device`, device tokens of phones only, and only for
   the relay that PURSS uses). PURSS returns a **fetch credential** (`purss_push_…`, only its SHA-256 stored) that the
   page hands to native code: Android's private preferences, or the iOS Keychain in an access group shared with the
   notification service extension. It reaches one thing, this phone's waiting notifications (with the number of New
   items for the icon), so the extension never holds the device token.
2. **Waking.** When a notification is made or grows, the API gathers for three seconds and then asks the relay to wake
   each of the account's registered phones that has something it hasn't been handed (`POST <relay>/v1/notify
   {"handle"}` through the safe fetcher), at most once a minute per phone. A wake that quiet hours held back or a
   restart lost is sent by the maintenance tick, which runs once a minute and wakes each phone with something it wasn't
   handed that arrived after its last wake.
3. **Fetching.** The relay sends FCM a data message `{"purss":"1"}` (high priority, one collapse key, so an offline phone
   gets one wake that fetches everything waiting) and APNs an alert with fixed text and `mutable-content`. On Android
   `PurssMessagingService` (it extends the plugin's service and replaces it in the manifest, so new push addresses
   still reach the page) calls `POST /api/push/pending` with the fetch credential and shows each notification itself;
   on iOS the notification service extension does the same and replaces the alert's text with the newest, adding
   "N more in your PURSS" when there are several, and keeps the fixed text when the fetch fails or finds nothing.
4. **Tapping** opens `purss://open?item=…&source=…`: the item in its source, the source, or Home. It only navigates.

What reaches the phone follows the rules that decide what reaches the bell (`services/notifications.ts`): quiet hours
are enforced on the server (no wake during them; the first maintenance tick after they end wakes the phone once);
each phone is handed each notification once, and again when its text grows ("3 new from …"), which replaces the one
shown; at most five per wake, oldest first; read notifications are not handed. Titles are as in the bell, and the body
only with *Show item titles in notifications*. On Android a notification is private on a locked screen that hides
contents (it shows "Something new in your PURSS").

**The count on the icon.** Every fetch answers with `newItems`, the New items as the sidebar adds them up, also with
notifications off or nothing waiting; while the app is open the page sets the same number through
`PurssDevice.setBadge`. On iOS the extension sets the alert's `badge`. Android has no badge of its own: PURSS's
notifications on the `workspace` channel carry numbers that add up to the count, which launchers that show numbers
use, and with no notification there is no badge. The FOSS build shows no notifications, so it has no badge.

**What each party sees**

| Party | Sees | Never sees |
| --- | --- | --- |
| Push relay | The phone's push address and IP address when it registers; a handle and the sending server's IP address for each wake, and when | Accounts, PURSS addresses (except as the sender's IP), notification text, items |
| Google (FCM) or Apple (APNs) | That the app on that phone received a push from the project's credentials, and when; on iOS the fixed text "You have something new in your PURSS." | Which PURSS, any notification text |
| PURSS | The handle; which notifications it handed to the phone | The phone's push address |
| The phone | The texts it fetches from its own PURSS | |

Someone who copied a handle could only make the relay wake that phone with no content, within the relay's per-handle
limit. The relay stores only the SHA-256 of each handle. Turning notifications off while offline is finished at the
app's next start: until PURSS and the relay have both heard it, the app keeps a note and tells them again.

**Which relay.** The app registers with `OFFICIAL_PUSH_RELAY` in `packages/domain/src/distribution.ts`, the only relay
that holds its credentials; a PURSS whose `PURSS_PUSH_RELAY_URL` names another relay can't reach it, and Settings says
so. `PURSS_PUSH_RELAY_URL` unset (or `official`) is the project's relay; empty or `off` turns phone notifications off
(see [self-hosting](../../docs/self-hosting.md)). Android debug builds can be given a local relay and a stand-in push
address (`-PpurssPushRelay`, `-PpurssPushDebugToken`); release builds carry empty values.

### Setting up push (the operator of an app build)

Phone notifications need credentials that belong to whoever publishes the app. The project's own build has them; a fork
that publishes its own app does these steps once:

1. **Firebase project** (console.firebase.google.com): add an Android app with the package `app.purss` (or your own id),
   enable the Cloud Messaging API (V1), download `google-services.json` to `apps/mobile/android/app/` (not committed),
   then `npm run sync -w @purss/mobile` and build.
2. **FCM service account:** *Project settings → Service accounts → Generate new private key*. Keep the JSON outside Git,
   on the relay host.
3. **APNs key:** in the Apple developer account, *Keys → +*, enable Apple Push Notifications service, and download the
   `.p8` once; note its Key ID and the Team ID. Enable Push Notifications and the keychain group on the App ID (see
   [iOS](#ios-what-to-do-on-a-mac), step 6).
4. **Relay:** deploy [`apps/push-relay`](../push-relay/README.md) behind HTTPS with both credentials, back up its data
   volume's `handle-secret`, and put its address in `OFFICIAL_PUSH_RELAY` before building the apps and the PURSS image.

Real delivery through FCM and APNs has been tested only against fakes of both services; on the emulator the push itself
is replaced by a debug broadcast (see [below](#notifications-on-the-emulator)). The iOS extension, Keychain sharing and
tap handling have never been compiled or run. When a fetch on iOS finds nothing because another wake already took it,
the fixed text shows, since iOS doesn't let an extension drop an alert without a special entitlement. There are no
notification actions (marking read from the notification), no per-device choice of what to receive, and a phone's
notification isn't cleared when the item is read elsewhere.

## Background downloads and home-screen panels

Three things need native code that runs without the page: automatic downloads while the app is closed, stopping a
download on the wire, and the home-screen panels (To read, To listen, New, a chosen collection, a chosen source). The
page and the native side share one set of rules (`packages/domain/src/downloads.ts`: what is wanted, sizes, the limit,
cleanup); which items to fetch is PURSS's answer to `POST /api/downloads/plan`, asked by both the open app and the
background job, so Kotlin and Swift never restate the rules.

- **Download plugin.** `PurssDevice` (Android `app.purss.device`, iOS `App/PurssDevice`) does every download:
  `download({id, url, path, maxBytes})` writes `<path>.part` and renames it when complete, `cancel({id})` closes the
  connection and deletes the partial file, and `progress` events report. Always the publisher's https file, straight
  from the publisher; no download is larger than 4 GB, and one whose declared or received size outgrows the room left
  under the limit stops and is marked failed.
- **Android, app closed.** Downloads started in the app run in a one-time WorkManager job as a `dataSync` foreground
  service with a *Downloading to this device* notification, so a swipe away doesn't stop one; a job the system stops
  runs again and continues (a cut-off transfer keeps `<path>.part` and asks `Range` with `If-Range` from a strong ETag
  or Last-Modified; a publisher without either sends the whole file again). Started from the background, where
  Android 12 and later refuse a foreground service, it runs as ordinary work. A lost connection while the app isn't on
  screen is retried with back-off, at most 8 runs. The automatic downloads job is periodic work every hour that needs a
  connection, battery not low and storage not low, and checks Wi-Fi or Ethernet when it runs if *Only on Wi-Fi* is on;
  it does nothing while the app is in the foreground. The panels' refresh is periodic work every 15 minutes (the
  shortest WorkManager allows) that needs only a connection.
- **iOS, app closed.** A second background URLSession (`app.purss.downloads.page`) lets the system finish a transfer and
  relaunch the app to move the file into place; a processing task (earliest one hour after the app goes to the
  background) runs the automatic downloads and refuses cellular when Wi-Fi only is on; a refresh task (earliest 15
  minutes) updates the panels. The system chooses when. iOS cancels background transfers of an app the person swipes
  away; the resume data then lets the next start continue.
- **Only the file in flight.** While the app is closed only the file being fetched goes on; the page's next queued
  downloads, and each item's text, notes and publisher's page, wait until the app runs again. The background job doesn't
  apply *Remove downloads when finished* or refresh downloaded items' text; the app does both when it next syncs.
- **Credentials.** The job reads the device token from the same secure storage the page uses and never copies it. The
  page mirrors the account, settings and what it already has to native storage (`PurssDevice.setBackground`). A 401
  from PURSS makes the job delete the downloads, the mirror and everything the panels kept, cancel its schedules, and
  leave a flag; at its next start the page sees it and runs the app's own lost-connection path.
- **Panels.** Five kinds, each its own entry in the launcher's widget list. Items of private sources are never in a
  panel, as their titles are never in notifications. The native side fetches each placed panel's list itself
  (`GET /api/items?…&limit=10&exceptPrivate=1`, the table in `widget-lists.json`, checked by the Kotlin and page tests;
  Swift follows it) and keeps the last list when a request fails. Panels hold titles, never the token or any address
  of the PURSS. A row opens `purss://open?item=<id>`, a heading `purss://open?list=<key>`. Android draws as many rows as
  the panel's height holds (at most 8); the episode's play/pause on Android goes to the app's running Media3 session,
  and opens the episode when the app isn't running. Placing a Collection or Source panel on Android opens a list of the
  PURSS's collections or followed sources (without private ones); on iOS 17 and later the widget's own configuration
  chooses, and a new one shows *Loading…* until the app's next refresh. iOS 15 and 16 offer only To read, To listen and
  New. The iOS panels have no play/pause: tapping the episode opens it.
- **Limits that are Android's own.** A force-stopped app has no scheduled jobs and its panels' taps do nothing until the
  app runs again; WorkManager skips a periodic run asked for before its interval is up; the system decides when each
  job runs (battery, Doze, standby buckets), so a panel may be older than 15 minutes; some makers' battery managers
  stop a foreground service anyway, and the next run continues.
- **The page's download records** live in the WebView's local storage. A record of a download finished just before the
  app was stopped may be lost, and its files are then swept at the next start; background downloads don't depend on
  this (`record.json`).

## Passkeys in the app

The app signs in and confirms it's you with the phone's own passkeys (`@capgo/capacitor-passkey`), the same
passkeys a browser uses on the PURSS's address, once the PURSS vouches for the app:

- **Android:** the PURSS sets `PURSS_APP_ANDROID_CERT_SHA256` to the SHA-256 fingerprint of the key that signs
  the APK (`keytool -list -v -keystore release.jks`, or the debug key's for a debug build) and serves
  `/.well-known/assetlinks.json`. Nothing to change in the app; any PURSS that vouches works.
- **iOS:** the PURSS sets `PURSS_APP_IOS_APP_ID` (`TEAMID.app.purss`), and the app has to be built with that
  domain: `PURSS_APP_PASSKEY_DOMAINS=purss.example npm run sync -w @purss/mobile`.

Elsewhere the app signs in with an email address and password; links from emails (password reset,
confirming an address, invitations) are pasted into the app.

## Try it on the emulator

```sh
npm run build                                           # the PURSS's own build, served at /app/
node apps/mobile/scripts/emulator-workspace.ts 19990   # prints an email address and password; Ctrl+C deletes everything
adb reverse tcp:19990 tcp:19990                          # the emulator's localhost is this computer
adb install -r apps/mobile/android/app/build/outputs/apk/full/debug/app-full-debug.apk
```

Where SELinux is enforcing (Fedora, for one), the emulator's default software renderer (SwiftShader) is blocked
(`execheap`) and qemu crashes during boot: start it with `-gpu lavapipe`, e.g.
`emulator -avd <avd> -no-window -no-audio -no-snapshot -gpu lavapipe`.

The app opens on the official server's sign-in; press **Use another server**, type
`http://localhost:19990`, and sign in with the email address and password it printed. The app
remembers that server for next time. Plain HTTP works only for addresses on this device or the local network
(the rule in `packages/domain/src/workspace-address.ts`, shared with the extension); a PURSS
elsewhere needs HTTPS. Debug builds let Chrome's
`chrome://inspect` (or `adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`) inspect
the app's page.

### Background downloads and the panels on the emulator

The background job is a WorkManager periodic job (namespace `androidx.work.systemjobscheduler`). With
the app closed (Home, then `adb shell am kill app.purss`), find its id with
`adb shell dumpsys jobscheduler | grep app.purss` and run it with
`adb shell cmd jobscheduler run -f -n androidx.work.systemjobscheduler app.purss <id>`.
WorkManager skips a periodic run that comes before its hour is up ("executed before schedule" in
logcat); on an emulator, `adb root` and moving the clock forward an hour lets it run. A force-stopped
app has no jobs until it is opened again (Android's rule). Its log tag is `PurssBackground`.
Downloads started in the app run in their own one-time job (`PageDownloads`, log tag `PurssDownloads`) as a
foreground service with a *Downloading to this device* notification; swipe the app away during one and it goes on. The
home-screen panels are in the launcher's widget list under *PURSS* (To read, To listen, New, Collection,
Source); their refresh is its own periodic job (every 15 minutes, log tag `PurssWidgets`), run the same way.
Kotlin unit tests:
`./gradlew testFullDebugUnitTest`.

### Notifications on the emulator

Without Firebase, a debug build can still go through everything but the push itself: point it at a
local relay with a stand-in push address, and run the messaging service's code with a broadcast that
exists only in debug builds.

```sh
PURSS_RELAY_PORT=8950 PURSS_RELAY_DATA_DIR=/tmp/purss-relay node apps/push-relay/src/main.ts &
PURSS_PUSH_RELAY_URL=http://localhost:8950 node apps/mobile/scripts/emulator-workspace.ts 19990
adb reverse tcp:19990 tcp:19990 && adb reverse tcp:8950 tcp:8950
cd apps/mobile/android && ./gradlew assembleFullDebug -PpurssPushRelay=http://localhost:8950 -PpurssPushDebugToken=emulator-debug-token-0123456789
```

Connect, turn on Settings → This device → Notifications on this phone (the system asks), make
something new reach the bell, then `adb shell am broadcast -a app.purss.DEBUG_PUSH -n
app.purss/.DebugPushReceiver`: the notification is fetched from the PURSS and shown, and
tapping it opens its item. (The PURSS's own wake goes nowhere here: it never calls an address on
this machine.)

## iOS: what to do on a Mac

The iOS project has not been compiled: it can't be on Linux. Its texts (the widgets' headings, descriptions and
empty messages in `Widgets/WorkspaceWidget.swift`, `Widgets/PanelChoice.swift` and `Widgets/WidgetLists.swift`, and the
notification extension's "more in your PURSS" line) are still written in the Swift files, not in `packages/translations`: the
project lists its files one by one, so a generated Swift file has to be added to its targets in Xcode first. On a Mac with
Xcode 16 or later:

1. `npm install && PURSS_WEB_BASE=/ npm run build -w @purss/web && cd apps/mobile && npx cap sync ios`, then
   `npx cap open ios` (opens `ios/App/App.xcodeproj`; plugins come through Swift Package Manager).
2. In *Signing & Capabilities*, choose your team for both the **App** and **ShareExtension**
   targets. If you change the app id, change both bundle ids (`app.purss`,
   `app.purss.ShareExtension`) and the app group everywhere it appears.
3. Register the app group `group.app.purss` in your Apple developer account (or let Xcode
   do it) and make sure both targets list it under *App Groups*; the files are
   `App/App.entitlements` and `ShareExtension/ShareExtension.entitlements`, and the same id is in
   `capacitor.config.ts` and `ShareExtension/ShareViewController.swift`.
4. Set the version from the checkout (the same number as Android's; the Xcode project has no step that reads it), in `ios/App`:
   `xcrun agvtool new-marketing-version "$(node ../../../../scripts/version.ts --dotted)"` and
   `xcrun agvtool new-version -all "$(node ../../../../scripts/version.ts --plain)"`.
5. Check *Background Modes → Audio*, *Background fetch* and *Background processing* on the App target
   (already in `Info.plist`, with `BGTaskSchedulerPermittedIdentifiers` = `app.purss.downloads` and
   `app.purss.widget-refresh`) and that
   the `purss` URL type is listed under *Info → URL Types*.
4a. The **Widgets** target (WidgetKit, `app.purss.Widgets`): choose your team and make sure it
   lists the app group under *App Groups* (`Widgets/Widgets.entitlements`). Check the five panels (Collection
   and Source on iOS 17: edit the widget to choose), small, medium and large, light, dark and e-ink looks, that
   tapping a row opens the item (`purss://open?item=…`) and a heading its list (`purss://open?list=…`), and
   that the panels refresh with the app closed
   (`_simulateLaunchForTaskWithIdentifier:@"app.purss.widget-refresh"`).
4b. The background job: with a connected PURSS and automatic downloads on, send the app to the
   background, pause in the debugger and run
   `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"app.purss.downloads"]`,
   then open the app: the episode shows as Downloaded. Also check the Keychain read with the device
   locked after first unlock, and that a transfer still running when the task expires is finished
   when the system relaunches the app. The Swift was written without a compiler; the signatures and
   behaviour to check on the first build are `call.reject(_:_:_:_:)` with data and `notifyListeners`,
   `registerPluginInstance` in `capacitorDidLoad`, `URLSession.allTasks`, `withTaskCancellationHandler` with a checked
   continuation, `BGTaskScheduler.register`, `containerBackground(_:for:)`, the `NoRedirects` session delegate with the
   async `data(for:)`, and for the panels `AppIntentConfiguration` with `AppIntentTimelineProvider`, `if #available`
   inside the `WidgetBundle`, `WidgetCenter.getCurrentConfigurations` with `widgetConfigurationIntent(of:)`, the header
   band reaching the widget's edges (`widgetContentMargins` on iOS 17), the widgets' own asset catalog (`PanelLogo`), and
   App Intents metadata in an extension deployed at iOS 15.
6. Notifications (the code is in `ios/App/App/PurssPushPlugin.swift` and `ios/App/NotificationService/`):
   - Add the *Push Notifications* capability to the **App** target (`aps-environment` in
     `App/App.entitlements`; Xcode switches it to production for distribution).
   - Register the keychain access group `app.purss.shared` (it appears as
     `$(AppIdentifierPrefix)app.purss.shared` in `App/App.entitlements`,
     `NotificationService/NotificationService.entitlements` and both `Info.plist` files as
     `PurssKeychainGroup`) and make sure both the **App** and **NotificationService** targets list it
     under *Keychain Sharing*. On the **App** target the app's own group (`app.purss`) must stay
     listed first: Keychain items without a named group (the device token) go to the first group, and
     the extension must never be able to read the device token. Choose your team for the **NotificationService** target too
     (bundle id `app.purss.NotificationService`; change it with the app id).
     The extension reads only that Keychain item, so it has no app group; the **App** target carries
     both, the app group shared with **ShareExtension** and **Widgets** and the keychain group shared
     with **NotificationService**.
   - In the Apple developer account create an APNs auth key (*Keys → Apple Push Notifications
     service*, a `.p8` file). Note its Key ID and your Team ID, and give the three to the relay
     (`apps/push-relay`).
   - On a device, check: Settings → This device → Notifications on this phone asks for permission;
     a notification from your PURSS shows its real text, not "You have something new in your
     PURSS."; tapping it opens the item (the same `purss://open` handling as a widget's row);
     turning the setting off stops notifications; and disconnecting the app, or the background job
     finding the device disconnected in the PURSS, stops them too and empties the widget.
7. Build and run on a simulator, then a device, and check: connecting (the browser returns to the
   app), reading, playing with the screen locked and the lock-screen controls, downloading and
   reading in airplane mode, and sharing a link from Safari (Share → PURSS).
8. For distribution: an App Store Connect record, an archive (*Product → Archive*) and TestFlight.
   App Review needs a reachable demo PURSS with sample data.

## The official server

The apps and the browser extension connect to the official server unless the person chooses
another one. Its address is `OFFICIAL_WORKSPACE_ORIGIN` in `packages/domain/src/distribution.ts`:
change that one value when the server moves (an empty string shows only the address field).
The app opens straight on its sign-in; nobody has to type or confirm a server.

Once the app is live in Google Play or the App Store, put the listing's address in `STORE_LISTINGS`
in `packages/domain/src/distribution.ts`: Settings → Connected apps and the website then show its
store button instead of naming the store as "not … yet".

Things to watch on iOS: `@mediagrid/capacitor-native-audio` and `@aparajita/capacitor-secure-storage`
must resolve through Swift Package Manager (both ship a `Package.swift`); WebCrypto (`crypto.subtle`,
used for PKCE) is expected in the `capacitor://` page.
